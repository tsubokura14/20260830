# トラブルシューティング

実装・運用中に発生した問題と対処の記録。再発時の調査時間短縮のために残す。

## E2E（Playwright）関連

### 1. E2E_USER_NAME等を`.env.test.local`に設定しても未設定扱いになる

**症状：** `.env.test.local` に `E2E_USER_NAME` / `E2E_USER_PASSWORD` / `E2E_BASE_URL` を書いても、`e2e/golden-paths.spec.ts` の `test.skip` 判定が働き、全テストがスキップされてしまう。

**原因：** `playwright.config.ts` が `.env.test.local` を読み込んでいなかったため。Next.js自体は `.env.local` を自動読込するが、Playwrightにはそのような自動読込機能はなく、明示的に読み込むコードが必要。結合テスト用の `vitest.integration.config.mts` では既に `dotenv` で読み込んでいたが、`playwright.config.ts` には同様の処理がなかった。

**対処：** `playwright.config.ts` の先頭で明示的に読み込む。

```ts
import { config } from "dotenv";
config({ path: ".env.test.local" });
```

読み込みはconfigファイルの評価時（テスト実行より前）に行う必要がある。`baseURL: process.env.E2E_BASE_URL ?? ...` のようにconfigファイル自身が環境変数を参照する箇所があるため、spec側でdotenvを読み込んでも手遅れになる。

### 2. `getByRole('link', { name: '記録' })` がstrict mode違反になる

**症状：** `strict mode violation: getByRole('link', { name: '記録' }) resolved to 2 elements`

**原因：** Playwrightの`getByRole(..., { name })`はデフォルトで部分一致。ヘッダーロゴ「実績記録アプリ」にも「記録」という文字列が含まれるため、`/achievements/new` への「記録」リンクと2つマッチしてしまう。

**対処：** `{ name: "記録", exact: true }` を指定し、完全一致に絞る。

### 3. `confirm()`ダイアログのハンドラを`click()`の後に登録すると自動キャンセルされる

**症状：** 削除ボタンを押しても、期待したエラートースト（またはDBから実際に削除された結果）が反映されない。

**原因：**
```ts
await page....getByRole("button", { name: "削除" }).click();
page.once("dialog", (dialog) => dialog.accept()); // click()の後に登録している
```
`click()`実行時にアプリ側の`window.confirm()`がその場でダイアログを発生させる。Playwrightは「ダイアログ発生時にリスナーが未登録なら自動キャンセル」する仕様のため、`click()`の後にリスナーを登録すると間に合わず、確認は常に「キャンセル」扱いになる。

**対処：** ダイアログを発生させる操作（`click()`）より**前**にリスナーを登録する。

```ts
page.once("dialog", (dialog) => dialog.accept());
await page....getByRole("button", { name: "削除" }).click();
```

## アプリ本体のバグ

### 4. 実績が紐づくグループを削除しようとするとサーバーエラー画面になる

**症状：** 「実績が紐づくグループは削除できない」というE2Eテストで、期待していたエラートースト（「紐づく実績があるため削除できません」）ではなく、Next.jsの汎用サーバーエラー画面（`This page couldn't load`）に遷移してしまう。

**原因は2段階あった。**

1. [src/actions/groups.ts](../src/actions/groups.ts) の `deleteGroupAction` は、DB制約違反を検知するために以下のようにエラーコードを比較していた。

   ```ts
   const FOREIGN_KEY_VIOLATION = "23503"; // foreign_key_violation
   ...
   if (error.code === FOREIGN_KEY_VIOLATION) {
     return { error: "紐づく実績があるため削除できません" };
   }
   ```

   しかし `drizzle/schema.ts` の `achievements.groupId` は `onDelete: "restrict"` を指定しており、この場合PostgreSQLが実際に返すSQLSTATEコードは `23503`（foreign_key_violation）ではなく **`23001`（restrict_violation）** である（Neonへの実DELETEで実測して確認）。

2. コードを`23001`に直しても再現し続けた。原因を追ったところ、アプリは`@neondatabase/serverless`を直接使わず**Drizzle ORM(`db.delete(...)`)経由**でクエリを実行しており、Drizzleはドライバが投げた生の`NeonDbError`（`code: '23001'`を持つ）を**自身のエラーオブジェクトでラップして**`throw`していた。実際に同じ削除処理を再現して調べたところ、

   ```
   error.code        → undefined（存在しない）
   error.cause.code  → '23001'（実際はここにネストされている）
   ```

   という構造になっていた。そのため`error.code === "23001"`という比較は常に`false`になり、依然として`catch`内で再`throw`され、ハンドリングされない例外としてサーバーエラーになっていた。

**対処：** コードを`23001`に直した上で、比較先を`error.cause`に変更。

```ts
// ON DELETE RESTRICTによる削除拒否は23503(foreign_key_violation)ではなく
// 23001(restrict_violation)としてPostgreSQLから返される。
const RESTRICT_VIOLATION = "23001";
...
// DrizzleはNeonドライバの生エラー(code付き)をラップしてthrowするため、
// コードは error.code ではなく error.cause.code に入っている。
const cause = error instanceof Error ? error.cause : undefined;
if (
  typeof cause === "object" &&
  cause !== null &&
  "code" in cause &&
  (cause as { code?: string }).code === RESTRICT_VIOLATION
) {
  return { error: "紐づく実績があるため削除できません" };
}
```

**教訓：**
- `ON DELETE RESTRICT`制約違反と一般的な外部キー違反（INSERT/UPDATE時など）はPostgreSQL上で異なるSQLSTATEコードになる。
- Drizzle ORM(`neon-http`アダプタ)経由でクエリを実行した場合、DBドライバの生エラーは`error`自体ではなく`error.cause`にラップされる。ORM/ドライバを経由するとエラーオブジェクトの形が変わりうるため、`.code`のような特定プロパティで分岐する処理は、実際に例外を発生させて`console.log(Object.keys(error))`等で構造を確認してから実装するべき。
- 単体テスト・結合テストは`rejects.toThrow()`のみでエラーコードの値までは検証しておらず、この不一致はE2Eテストで初めて顕在化した。
