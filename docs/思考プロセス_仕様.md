## フレームワーク・スタイリング（Next.js / Tailwind）

- Next.js はユーザーが最初から想定していたスタックの一つであり、Server Actions を使えば画面とAPIを1つのコードベースに収められる。特に異論なく採用。

この2つは大きな検討なく決定。

## DB / ORM：Supabase → Neon への転換

### 当初の判断（Supabase採用）

最初はSupabaseを次の理由で採用と判断した。

- ホスティング済みPostgres + Auth + 型生成が一体になっており、個人開発でインフラ管理の手間を減らせる。
- 仕様書4.1で決めた「パスワードハッシュ化」「簡易パスワード認証」を、Supabase Authに任せれば自前実装せずに済む（パスワードのハッシュ化・セッション管理はSupabaseが担う）。
- サインアップ機能は使わず、初期ユーザーのみダッシュボードから作成すればよい（仕様書で「サインアップ不要・初期ユーザーのみ」と決まっていたことと相性が良い）。

### 判断：NeonへのDB変更依頼

その後「Supabaseではなく Neon に修正できますか」という要望が入った。

Neonは純粋なサーバーレスPostgresホスティングであり、Supabaseと違って**認証機能を内蔵していない**。この違いをまず明示する必要があると判断した。

**トレードオフの整理**

| | 内容 |
|---|---|
| Neonのメリット | サーバーレス環境に最適化されたPostgres。コネクションプーリング内蔵で、Vercelとの相性が良い |
| Neonのデメリット | 認証（パスワードハッシュ化・セッション管理）を自前実装する工数が発生する（Supabaseなら不要だった作業） |

**結論：** 個人利用前提のアプリであることを踏まえ、認証を自前実装する工数増は許容範囲と判断し、Neonへの変更を確定した。

### ORMの選定（Drizzle ORM）

Supabaseの公式クライアントはSupabase専用のため、Neonに変更する以上、別途ORM/クエリビルダーが必要になる。

- Neon公式が `@neondatabase/serverless` ドライバとの組み合わせで Drizzle ORM を推奨しており、実績のある組み合わせであることを理由に採用。
- 副次的なメリットとして、Drizzleはスキーマ定義（`drizzle/schema.ts`）からTypeScriptの型を直接推論できる。Supabaseのように `supabase gen types` のような別コマンドでの型生成ステップが不要になり、スキーマ変更時の型同期の手間が減る。

## 認証：自前実装（bcrypt + JWT）

Neonへの変更に伴い、認証は自前実装が必須になった。方式は次の理由で決定。

- 仕様書4.1で「パスワードは平文で保存せず、ハッシュ化する」とすでに決まっていたため、ハッシュ化ライブラリとして実績のある `bcrypt` を採用。
- セッション管理は、Cookieベースの `httpOnly` JWTセッションとした。JWTの発行・検証には `jose` を使う。
  - 理由：サインアップ機能を持たず初期ユーザー1人のみという小さいスコープに対して、フル機能の認証ライブラリ（NextAuth等）を導入するのは過剰と判断した。bcrypt（ハッシュ化）+ JWT（セッション）という最小構成で仕様書の要件（パスワード認証のみ、リセット不要）を満たせる。
- ログイン試行回数の制限（仕様書6章で推奨と記載していた「ブルートフォース対策」）は、Server Actions内での簡易なレートリミットとして実装する方針とした。この時点では具体的な閾値（何回失敗で何分ロックするか）は未決定のままとした（[後述の検討](#ログイン試行回数推奨設定を採用)で確定）。

## バリデーション：Zod

- 仕様書4.5で決めた文字数制約（テーマ300文字、内容3000文字、ユーザー名50文字、パスワード8文字以上）を実装に落とし込む必要があった。
- Zodスキーマを `schemas/` ディレクトリに一元管理し、**クライアント側（フォーム）とサーバー側（Server Actions）の両方から同じスキーマを参照する**設計とした。仕様書4.5「バリデーションはフロントエンドとバックエンドの両方で行う」という要件を、ルールの二重管理なしに満たすための判断。

### 追加提案：react-hook-form + @hookform/resolvers/zod

Zodスキーマを定義するなら、フォーム側もそのスキーマをそのまま使えるライブラリと組み合わせた方が実装量が減ると考え、`react-hook-form` との組み合わせを追加提案した。ユーザーはこの提案を含めて受け入れ。

## 日付処理：date-fns

可視化画面（日移動・年月選択）と実績数確認画面（月単位のヒートマップ生成）で日付計算が頻出することが仕様書の段階で分かっていたため、軽量な日付ユーティリティとして `date-fns` を追加提案した。

## ヒートマップ：専用ライブラリを使わない判断

仕様書5.5で「週7カラム・月単位で分割・4段階の色分け」という具体的な仕様まで固まっていたため、これは単純なグリッド生成の範囲に収まると判断した。

専用のチャート/ヒートマップライブラリを追加すると依存が増えるだけでメリットが薄いため、Tailwindのグリッドと配列生成による自前実装を提案し、採用。

## 状態管理：Zustandの適用範囲を絞る判断

当初のスタック指定に Zustand が含まれていたが、そのまま「グローバルなクライアント状態管理」として無条件に使うと、フィルター状態（可視化画面・実績数確認画面の年月・グループ選択）もZustandで持つ設計になりがちだった。

**懸念：** Zustandの状態はリロードで消え、URLで共有もできない。可視化画面・実績数確認画面のフィルター状態は、本来リロード耐性や共有可能性があった方が便利なはず。

**判断：** フィルターは Zustand ではなく**URLクエリパラメータ**（`useSearchParams` / 必要なら `nuqs`）で持たせることを提案し、採用。Zustandは「モーダルの開閉状態」のような、URLに残す意味のない一時的なUI状態にのみ使う、という役割分担に落ち着いた。

サーバーデータ（実績・グループそのもの）についても、単一ユーザーの個人アプリであるためクライアント側でキャッシュを持つ複雑さは不要と判断し、Server Component / Server Actions経由で都度取得する方針とした（Zustandで保持しない）。

## アーキテクチャ全体の方針

- **Server Actions中心**：実績・グループのCRUDはAPI Routesではなく Server Actions に集約する。フォーム送信からDB操作までを型安全につなげられ、Zodスキーマをサーバー側バリデーションにもそのまま使えるため。
- **`(protected)` ルートグループ**：認証必須の4画面（可視化・実績入力・グループ管理・実績数確認）を1つのルートグループにまとめ、`layout.tsx` 1箇所で未ログイン時のリダイレクトを扱う設計とした。画面ごとに個別の認証チェックを書く必要をなくすための判断。
- **画面とディレクトリの対応**：仕様書5章で定義した5画面（ログイン／可視化／実績入力／グループ管理／実績数確認）に、`app/` 配下のルートをそのまま対応させ、仕様と実装のずれが起きないようにした。
- **`drizzle/schema.ts` を単一の情報源にする**：テーブル定義をコードで持ち、グループ削除時の `ON DELETE RESTRICT`（仕様書4.4）などの制約もスキーマに含める。`drizzle-kit generate` でマイグレーションを生成し、スキーマ変更を常にコードで追跡できるようにした。

## テスト戦略の検討

「単体・結合・E2E・総合の観点でテストをどう保障するか」という問いに対して検討した。

**前提となる考え方：** 個人開発・単一ユーザー前提のアプリに、全層を網羅する厳格なテスト体制を敷くのは過剰と判断した。理解度%管理やゲーミフィケーションをスコープ外にしたときと同じ理由で、コストに見合わない作り込みは避け、**費用対効果の高い層に比重を置く**方針とした。

- **単体テスト**：`schemas/`（Zod）、`lib/date.ts`、`lib/auth/` はDB・UIに依存しない純粋ロジックのため、もっともコストが低く価値が高い。特に仕様書4.5で決めた文字数の境界値テストを重点対象とした。
- **結合テスト**：仕様書4.4で決めた「グループ削除の `ON DELETE RESTRICT` 制約」「未設定グループへの自動割当」は、設計上とくに重要な業務ルールであるため、モックせず実DBに対して検証する方針とした。Neonのブランチ機能（テストごとに使い捨てDBを作れる）が、Neonを選定した理由の一つでもあったことから、ここで活用できると判断した。
- **E2E**：個人開発であることを踏まえ、網羅的なシナリオではなく「壊れたら気づく」ためのゴールデンパスのみに絞った（ログイン→登録→可視化への反映、削除制約、URLクエリでのフィルター状態保持の3点）。
- **総合テスト**：自動化コストに見合わないと判断し、**仕様書.mdをそのままチェックリスト化した手動確認**とした。特に2.2の「対象外」項目が実装に紛れ込んでいないかの確認は、コンセプト（積み上げ感重視・採点しない設計）を実装段階で崩さないためのセーフティネットとして重要と考え明記した。

ツールはVitest（単体・結合）とPlaywright（E2E）を採用。いずれもNext.js/TypeScriptとの親和性が高く、追加の学習コストが小さいことを理由とした。

**気づき：** このテスト戦略の検討の中で、ログイン試行回数の制限がこの時点で「100回失敗で60分ロック」になっていることに気づいた。一般的なブルートフォース対策としては5〜10回程度が実効性のある水準とされており、この閾値はやや緩い可能性がある。意図的な設定であれば問題ないが、総合テストのチェック項目としてこの閾値の妥当性を再確認することを推奨した。この指摘が、次節の見直しにつながる。

## 残課題の深掘り

前節までに洗い出した残課題（ログイン試行回数・エラー表示・env変数・CI・drizzle-zod）を1つずつ深掘りした。

### ログイン試行回数：推奨設定を採用

指摘した「100回失敗で60分ロック」は緩すぎるとの懸念に対し、「推奨設定でよい」との回答を得たため、**5回失敗で15分ロック**を採用した。一般的なブルートフォース対策の実効ラインとして提示した数値をそのまま採用。

### エラー表示：トースト通知（sonner）

「トーストにする」との回答を受け、具体的なライブラリとして `sonner` を提案し採用。Next.js App Routerとの親和性が高く追加のCSS設定がほぼ不要なこと、Server Actionsの戻り値をそのままトーストに渡しやすいことを理由とした。Server Actionsのバリデーションエラー・DB制約エラー（グループ削除時の `ON DELETE RESTRICT` 違反など）の表示先として使う。

### drizzle-zod：Zodが不要になるわけではないと整理

「二重管理で役割が被っているならZodは不要では」という疑問が出たため、役割の違いを整理した。

- **Drizzle**：DBのテーブル構造を定義する**サーバー専用**のスキーマ。実行時のバリデーション機能は持たない。
- **Zod**：フォーム・Server Actionsに渡ってくる**信頼できない値**を実行時に検証するためのライブラリ。
- **drizzle-zod**：DrizzleのスキーマからZodスキーマを**自動生成**するブリッジ。Zodを置き換えるものではない。

**結論：** drizzle-zodを導入しても「手書きZodスキーマの重複を減らす」効果はあるが、Zod自体はクライアント・サーバー双方のバリデーションエンジンとして引き続き必要と整理した。また、`users` テーブルの `passwordHash` とログインフォームの平文 `password` のように、DBカラムと入力項目が一致しない認証系のスキーマは、drizzle-zodでは自動生成できず手書きのZodが必要な点も明示した。

「二重に管理するものが発生するが役割が違う、という理解でよいか」という確認を受け、これは正しい理解であると回答した。drizzle-zodを使わない場合は「同じ制約を2箇所に手書きする」という人力の二重管理が発生するが、drizzle-zodを使えばZod側は自動生成されるため、人間が維持するのはDrizzleスキーマの1箇所だけになる。この整理に対し「であれば必要」との判断が示されたため、**drizzle-zodを採用**と確定した。実績・グループなどDBカラムと入力項目が一致するフォームは `createInsertSchema` 等で自動生成し、認証系のように一致しないものは引き続き手書きする、という適用範囲で運用する。

（補足：env変数の「1本／2本」という表現について、Postgresの接続文字列（URL）の本数を指しているか確認された。その理解で正しい旨を回答した。`DATABASE_URL`＝プーリング接続用、`DATABASE_URL_UNPOOLED`＝マイグレーション等の直接接続用。）

### 初期ユーザー登録：手動SQL方式に決定

「SEEDは手動でよい」との回答を受け、seedスクリプト（env変数経由）ではなく、**NeonのSQL Editorで一度だけ手動INSERTする方式**を採用した。

- 単一ユーザー・1回きりのセットアップという規模を踏まえると、スクリプトを書いて保守するコストが見合わないという当初の意見がそのまま採用された形。
- この決定により、`SEED_USER_NAME` / `SEED_USER_PASSWORD` という環境変数は不要になった。env変数は `DATABASE_URL`（プーリング接続、まずは1本のみで運用）と `JWT_SECRET` の2つに絞られた。

### 環境変数：確実に必要なものと代替案があるものを切り分け

「どのようなことを検討する余地があるか」という問いに対し、候補を分類した。

- **確実に必要（代替なし）**：`DATABASE_URL`（Neon接続情報は秘匿情報のため必ず環境変数化）、`JWT_SECRET`（自前JWT実装の署名鍵）。
- **検討の余地あり**：
  - `DATABASE_URL_UNPOOLED`：Neonはマイグレーション時に直接接続を推奨するが、個人開発規模ならプーリング接続1本で始め、必要になったら追加する段階的導入でも実用上問題ない可能性がある。
  - `SEED_USER_NAME` / `SEED_USER_PASSWORD`：初期ユーザー作成の一手法に過ぎず、単一ユーザー・1回きりのセットアップという規模を踏まえると、NeonのSQL Editorで一度だけ手動でINSERTする方式にすれば、seedスクリプトごとこれらの環境変数が不要になる可能性がある。

個人開発の規模では手動SQL実行の方がシンプルという意見を提示し、[初期ユーザー登録](#初期ユーザー登録手動sql方式に決定) のとおり手動SQL方式を採用した。

### CI：推奨設定を採用

GitHub Actionsで lint・型チェック・単体テスト・結合テストを実行する構成を提案し、「推奨設定でよい」との回答を得て採用した。

- 結合テストは `neondatabase/create-branch-action` / `delete-branch-action` を使い、PRごとに使い捨てのNeonブランチを作成→migration適用→テスト→削除する。技術仕様書5.2で決めた「Neonブランチを使った結合テスト」をそのままCI上で実現する形。
- E2E（Playwright）はビルド時間・実行コストが個人開発の規模に見合わないと判断し、CIには含めず、mainへのデプロイ前に手動実行する運用とした。
- デプロイ自体はVercelのgit連携が担うため、CIワークフローの役割は「mainマージ前の品質担保（lint・型チェック・単体・結合テストの通過確認）」に限定した。
