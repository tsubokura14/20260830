# 学習実績可視化アプリ 思考プロセス（要件）

> このドキュメントは、要件が固まるまでの検討過程を時系列で残したものです。
> 結論だけを見たい場合は [仕様書.md](./仕様書.md) を参照してください。

## 1. 動機

毎日学習をしている過程で、自分が成長しているのか、意味があることをしたのか不安になった。長期目標を達成するためにくじけそうになる感情の揺らぎを解決したい。

なので、**学習成果や積み上げの可視化**をしたい。

私（エンジニア）の例だが、コードのアウトプットはGitHubだけでよいと感じる。QiitaやZennなどでもよいような気がしなくもない。しかし、これらは毎日続けられるわけではない。それに、アウトプットというよりは自分がやったことの積み上げを可視化したい。

イメージとしては、日ごとのリスト表示で何を学習したか可視化できると嬉しい。

## 2. 検討の流れ

### 2.1 懸念：タスクを細分化すれば「積み上げ」が簡単になってしまうのでは？

- 当アプリは、本質的に成長することよりも「積み上げた感」を得ることを重視する方針とした（この判断自体への迷いは残る）。
- ただし、細分化を促すこと自体はよいことだと考える。

この懸念から、次の課題につながった。

### 2.2 課題：積み上げた感が、さらなる積み上げを促進する仕組みが欲しい

→ 積みあがると嬉しいUI/UX・ゲーミフィケーションを実装する方針とした。

なお、積み上げの粒度はユーザーに任せる。この時点では「todoの管理機能が必要」と考えていた（後に方針転換、[2.7](#27-結論todo管理からタスクcrudへの方針転換) 参照）。

### 2.3 判断：学習内容自体を入力項目にするか

- 検討：実際の学習内容と重複するため、テーマだけで十分ではないか。
- 残った課題：とはいえ、実際の学習内容と紐づけておきたい気持ちも残る。

### 2.4 構想：WBSベースのグループ表示

積み上げるタスクをグループごとに表示させたい。WBSを作成し、それを実績ベースでカレンダーにUI表示させるイメージ。

**反論1：それならWBSツールで良いのでは？**
→ 複数のWBSの実績を1つのビューで横断的に確認できる点、WBS以外（書籍のインプットのみ等）も記入できる点に価値がある。

**反論2：書籍のインプットだけでは理解できているか分からないのでは？**
→ 理解にもレベルがあるはず。アウトプット可能なレベルまで達していなくても、読んで理解できるのであれば「読んで理解できる」という実績があってよい。

### 2.5 課題：実績の種類・理解度をどこまで細分化するか

- 実績の種類として「インプット」「アウトプット」が考えられる。さらに細分化すると「動画教材」「AIとの壁打ち理解」「書籍」「ソースコード作成」「技術ブログ」など多岐にわたるが、具体化しすぎると使いにくくなる。「インプット」「アウトプット」よりもう一段掘り下げる程度のレイヤーにとどめたい。
- 理解度についても、単純な％表示だけでなく「自分で作成できる」「AIで実装できる」「読むことはできる」「メソッドの詳細は分からないが大枠は理解できる」のように細分化する案もあった。ただしエンジニア用途に寄りすぎるため、汎用性を高めるならもう少し抽象的な分類が必要かもしれない。
- 理解度は「100%」の状態を定義するのが難しいという問題もある。100%で登録した後にさらに理解が深まった場合、120%として登録し、それを新しい100として過去の実績を下方修正する、という仕組みも考えられる。

**Claudeからの指摘：タスクの重みづけ**
可視化側でタスクの重み（時間・難易度）を反映する（小さいタスクは小さいブロック、大きいタスクは大きいブロックとしてカレンダーに積む）方が、水増しへの耐性が高くなる。実装方針より先に「何を積むのか＝実績の単位」を決める必要がある、という指摘。

→ AI時代なので単純なアウトプット量そのものには意味がない。異なるジャンル・性質のものを一つの指標で測るのも難しい。タスクの内容が浅ければ、後で見返したときに「この日の自分は弱い」と気づくだけでよく、タスク日記のような使い方で十分。大切なのは作業の可視化そのものである。

### 2.6 判断：未完了のタスクを入力する必要はあるか

- WBSの二重管理は意味がない。WBSの攻略過程で「一項目も進んでいないが、前提・関連知識の理解ができた」というような、行き場のない実績のために使いたい。
- **結論：未完了タスクの入力は不要。** WBSを細分化して入力するというイメージは撤回する。WBSなど大枠の作業を進める際に取り組んだ、さらに細分化されたタスクや学びを記録する用途に絞る。

### 2.7 結論：todo管理から実績CRUDへの方針転換

[2.2](#22-課題積み上げた感がさらなる積み上げを促進する仕組みが欲しい) で「todoの管理機能が必要」としていたが、**実績のCRUD機能**に修正した。あわせて、以下を最終方針として確定した。

- 実績種別は「インプット」「アウトプット」の2種類のみにする。種別選択自体は本質ではなく、記録のハードルを上げたくない。また、2種類だけでも十分に意味がある。
- WBS等との二重管理を避けるため、学習内容との紐づけは行わない。紐づけ先がない粒度で実績を記載する。
- ゲーミフィケーションで学習促進を煽るというよりは、その日の学習内容を粒度高く棚卸しするイメージがよい。

## 3. 機能の洗い出し

上記の検討をもとに、実績管理機能（CRUD）として以下の項目・仕様を洗い出した。

### 3.1 実績（Achievement）

| 項目 | 内容 |
|---|---|
| id | 内部で自動生成 |
| グループid | 実績グループidを外部参照 |
| ユーザーid | ユーザーのidを外部参照 |
| 日付 | デフォルト当日、選択可能 |
| 実績種別 | インプット／アウトプット（必須） |
| テーマ | 必須 |
| 内容 | 任意 |

- 過去の実績は編集・削除してよい。水増ししても意味がないため、有効に使えるかはユーザーに委ねる。
- グループが存在しない場合は、「未設定」グループに自動で割り当てる。

### 3.2 実績グループ

| 項目 | 内容 |
|---|---|
| id | 内部で自動生成 |
| ユーザーid | ユーザーのidを外部参照 |
| 名前 | 必須、300文字まで |
| 色 | デフォルトでslate |

- 表示の際にグループ別で色を分けたい。WBSは使用しないので、ジャンル等（例：Java、TypeScript）で分けるのがよい。
- 実績と紐づいている場合、グループは削除できない。
- 実績グループ名はデフォルトで「未設定」のみ用意しておき、その他はユーザーが設定する。

### 3.3 ユーザー

| 項目 | 内容 |
|---|---|
| id | 内部で自動生成 |
| 名前 | 必須 |
| パスワード | 必須 |

- ログイン画面はログインのみ。初期ユーザーのみとし、サインアップ機能は不要（個人利用前提）。

### 3.4 画面構成

作成する画面は以下の4つ（＋ログイン）。

1. **可視化画面**
   - 実績を日ごとにリスト表示する
   - scrollで日を移動できる
   - 年・月を選択できるUIを別途作成する
   - グループでフィルターすることも可能にする（グループごとに色を変える）
   - 日単位・月単位・年単位で実績を可視化できるようにする
2. **実績入力画面**
3. **グループ管理画面**
4. **実績数確認画面**
   - 全体の実績数、グループごとの実績数を数値一覧とヒートマップで表示する
   - ヒートマップはカレンダー形式（週7カラム、月単位で分割）。GitHubのcontribution graphに近いイメージ
   - 期間ごとにフィルターできる
   - インプット・アウトプットの内訳も見れるようにする

### 3.5 バリデーション

| 項目 | ルール |
|---|---|
| テーマ | 上限300文字 |
| 内容 | 上限3000文字 |
| ユーザー名 | 上限50文字 |
| パスワード | 8文字以上（リセット機能は不要） |
| ヒートマップの色分け | 4段階（0件 / 1件以上 / 5件以上 / 10件以上） |

### 3.6 補足：DBサービス選定のきっかけ

Supabaseは無料枠が2プロジェクトしかないのに対し、Neonは無料枠で100プロジェクト作成可能。この差が、後の技術検討（[思考プロセス_仕様.md](./思考プロセス_仕様.md)）でNeonを選ぶきっかけの一つになった。
