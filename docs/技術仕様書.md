# 学習実績可視化アプリ 技術仕様書

> 本書は [仕様書.md](./仕様書.md)（機能・データモデル）を前提に、実装方式を定めるドラフトです。

## 1. 技術スタック

| 区分 | 採用技術 | 理由 |
|---|---|---|
| フレームワーク | Next.js (App Router) | Server Actionsで画面とAPIを1つのコードベースに収められる |
| スタイリング | Tailwind CSS | ユーティリティCSSで実装速度を優先 |
| DB | Neon (Serverless PostgreSQL) | サーバーレス環境向けに最適化されたPostgres。コネクションプーリング内蔵で、Vercelとの相性が良い |
| ORM | Drizzle ORM + `@neondatabase/serverless` | Neon公式が推奨する組み合わせ。スキーマ定義からTypeScript型を直接推論できるため、別途の型生成コマンドが不要 |
| 認証 | 自前実装（bcrypt + JWTセッションCookie） | Neonは認証機能を持たないため自前実装が必要。仕様書4.1のパスワードハッシュ化と合わせて、`bcrypt`でハッシュ化、`jose`でJWTを発行しhttpOnly Cookieに格納する方式を提案 |
| バリデーション | Zod + `drizzle-zod` | 仕様書4.5の文字数制約（テーマ300 / 内容3000 / ユーザー名50 / パスワード8以上）をスキーマとして一元管理し、クライアント・サーバー双方で共有。`drizzle-zod`でDrizzleスキーマからZodスキーマを自動生成し、制約の手書きによる二重管理を避ける（認証系など、DBカラムと入力項目が一致しないスキーマは引き続き手書き） |
| フォーム処理 | `react-hook-form` + `@hookform/resolvers/zod` | Zodスキーマをそのままフォームバリデーションに使え、実績入力・グループ管理フォームの実装量を減らせる |
| 日付処理 | `date-fns` | 可視化画面の日移動・年月選択、実績数確認画面のヒートマップ（月単位のカレンダー生成）で日付計算が頻出するため |
| クライアント状態管理 | Zustand | サーバーデータ本体・フィルター状態ではなく、モーダルの開閉など「URLに残す意味がない一時的なUI状態」のみを保持する用途に限定（3.3節） |

> Supabaseとの主な違い: Supabaseは Auth・型生成込みのBaaSでしたが、Neonは純粋なPostgresホスティングです。
> そのため**認証部分を自前で実装する工数が増える**点がトレードオフです。個人開発として許容し、Neonでの実装を確定した。

### 1.1 スタックに関する補足方針

- **ヒートマップに専用ライブラリは使わない**: 仕様は「週7カラム・月単位・4段階の色分け」という単純なグリッドのため、Tailwindのグリッドと配列生成で自前実装する。依存を増やすメリットが薄いため。
- **フィルター状態はZustandではなくURLクエリパラメータに持たせる**: 可視化画面・実績数確認画面の「選択中の年月・グループフィルター」は、リロードしても再現でき、URLで共有もできた方が便利なため、`useSearchParams`（必要なら `nuqs`）で管理する。

### 2.1 ポイント

- **画面と仕様書の対応**: `app/` 配下の各ルートは、仕様書5章の5画面（ログイン／可視化／実績入力／グループ管理／実績数確認）にそのまま対応させています。
- **`(protected)` ルートグループ**: 認証必須の4画面をまとめ、`layout.tsx` 1箇所で未ログイン時のリダイレクトを扱います。個別ページごとに認証チェックを書く必要がなくなります。
- **`actions/` に集約したServer Actions**: 実績・グループのCRUDはAPI Routesではなく Server Actions で実装します。フォーム送信からDB操作までを型安全につなげられ、`schemas/` のZodスキーマをそのままサーバー側バリデーションに使えます。
- **`schemas/` を単一の情報源にする**: 実績・グループなどDBカラムと入力項目がほぼ一致するフォームは、`drizzle-zod` の `createInsertSchema` 等で `drizzle/schema.ts` からZodスキーマを自動生成し、`schemas/` に配置します。認証系などDBカラムと入力項目が一致しないスキーマ（例: `users.passwordHash` に対する平文の `password` 入力）は手書きします。生成・手書きいずれも `react-hook-form` のクライアント側バリデーションと Server Actions のサーバー側バリデーションの両方から参照し、ルールの二重管理を避けます。
- **`drizzle/schema.ts`**: テーブル定義をコードで持ち、`ON DELETE RESTRICT`（仕様書4.4）などの制約もスキーマに含めます。`drizzle-kit generate` でマイグレーションSQLを生成し、`drizzle/migrations/` に出力します。
- **`types/database.ts` は不要**: Supabaseのような別コマンドでの型生成が要らず、`drizzle/schema.ts` からアプリ全体で型を直接importできます。

## 3. 各層の設計方針

### 3.1 データアクセス

- 一覧表示系（可視化画面・実績数確認画面）は Server Component から直接 Drizzle クライアントでクエリし、クライアント側に生データを持たせない。
- 作成・更新・削除は Server Actions 経由。実行後は `revalidatePath` で該当画面を再検証する。

### 3.2 認証

- サインアップ画面は作らない。初期ユーザーは、NeonのSQL Editorで一度だけ手動でINSERT文を実行して登録する（仕様書2.2・4.1）。単一ユーザー・1回きりのセットアップのため、seedスクリプトは用意しない。パスワードはあらかじめbcryptでハッシュ化した値を手元で生成し、INSERT文に埋め込む。
- ログイン成功時、`jose` でJWTを発行し httpOnly / Secure な Cookie に格納する。
- `middleware.ts` で Cookie 中の JWT を検証し、無効・未ログイン時は `/login` へリダイレクトする。
- ログイン試行回数の制限（仕様書6章で推奨）は Server Action 内でシンプルなレートリミット（失敗回数カラム＋一時ロック）として実装する。5回失敗で15分ロックする。
- Server Actionsのバリデーションエラー・DB制約エラー（グループ削除時の `ON DELETE RESTRICT` 違反など）は、トースト通知（`sonner`）で表示する。

### 3.3 状態管理の使い分け

| 状態の種類 | 保持方法 | 理由 |
|---|---|---|
| 実績・グループなどのサーバーデータ | Server Component / Server Actions 経由で都度取得 | 単一ユーザーの個人用アプリであり、クライアント側キャッシュの複雑さは不要 |
| 可視化画面・実績数確認画面の年月・グループフィルター | URLクエリパラメータ | リロード耐性・共有可能性のため（1.1節参照） |
| モーダルの開閉など一時的なUI状態 | Zustand | URLに残す意味がなく、コンポーネントを跨いで参照したい場合のみ使用 |

## 4. 決定事項（旧・未決定事項）

- ログイン試行回数の制限方式：5回失敗で15分ロック
- デプロイ先：Vercel（Neonとの組み合わせ）
- エラー表示：トースト通知（`sonner`）
- CI：GitHub Actionsでlint・型チェック・単体テスト・結合テスト（Neonの使い捨てブランチを利用）を実行する。E2Eはコスト対効果からCIには含めず、デプロイ前に手動実行する。デプロイ自体はVercelのgit連携に任せ、CIの役割はmainマージ前の品質担保に限定する。
- 初期ユーザー登録：seedスクリプトは用意せず、NeonのSQL Editorで一度だけ手動INSERTする。

### 4.1 環境変数

| 変数 | 用途 | 備考 |
|---|---|---|
| `DATABASE_URL` | アプリ実行時・マイグレーションで使うNeonのプーリング接続文字列 | まずはこの1本のみで運用し、`drizzle-kit`で問題が出た場合にのみ直接接続用の変数を追加する |
| `JWT_SECRET` | JWTの署名・検証鍵（`jose`が使用） | `openssl rand -base64 32` 等で生成 |

初期ユーザーは手動INSERTで登録するため、seedスクリプト用の環境変数（ユーザー名・パスワード）は不要。

## 5. テスト戦略

個人開発・単一ユーザー前提のため、全層を網羅的にカバーするのではなく、**費用対効果の高い層に比重を置く**方針とする。単体テストと、仕様書4.4の重要な制約を検証する結合テストを厚めにし、E2E・総合テストはゴールデンパスに絞る。

### 5.1 単体テスト（Unit）

- **対象**: 副作用のない純粋なロジック。`schemas/`（Zodスキーマ）、`lib/date.ts`（ヒートマップ用の日付計算）、`lib/auth/password.ts`（bcryptラッパー）、`lib/auth/session.ts`（JWT発行・検証）。
- **ツール**: Vitest。
- **重点**: 仕様書4.5の境界値（テーマ300文字、内容3000文字、ユーザー名50文字、パスワード8文字）のちょうど境界・超過ケースをZodスキーマ単体で検証する。DBもUIも不要でコストが低く、価値が高い領域。

### 5.2 結合テスト（Integration）

- **対象**: Server Actions が Neon(Postgres) に対して実際に読み書きし、Drizzleのスキーマ制約が期待通り効くか。特に仕様書4.4の設計上重要な制約を優先的に検証する。
  - グループに実績が紐づいている場合、削除が `ON DELETE RESTRICT` で失敗すること
  - グループ未指定時に「未設定」グループへ自動割当されること
- **環境**: Neonのブランチ機能を使い、テスト実行ごとに使い捨てのDBブランチを作成 → migration適用 → テスト → 破棄する構成とする。
- **ツール**: Vitestの別スイートとして分離し、モックせず実DBに対して実行する。

### 5.3 E2Eテスト

- **対象**: 実ブラウザでの一連の操作。網羅よりもゴールデンパスに絞る。
  1. ログイン → 実績登録 → 可視化画面に反映される
  2. グループ管理画面で、実績が紐づくグループの削除が拒否される（4.4のエラーメッセージ表示まで確認）
  3. 可視化画面・実績数確認画面のグループ/期間フィルターがURLクエリに反映され、リロードしても保持される（3.3節の設計の検証）
- **ツール**: Playwright。

### 5.4 総合テスト

自動化よりも、**仕様書.mdをそのままチェックリスト化した手動確認**とする。
- 5章の5画面がそれぞれ仕様通りに動くか
- 2.2「対象外」の項目が実装に紛れ込んでいないか（理解度％管理やゲーミフィケーション要素などを作り込んでいないかの確認）
- 非機能事項（ログイン試行回数制限の実際の閾値、ヒートマップの4段階配色が実データで見た目通りに出るか）
